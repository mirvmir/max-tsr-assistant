# Данные которые нужно подготовить для MVP

Версия 1.0.0 от 30 сентября 2026 года. Пути ниже заданы относительно корня будущего репозитория приложения. Это задания на получение и проверку данных; существующие в комплекте examples — только синтетические образцы формата. Production-ready данных и шаблонов в этом комплекте нет.

D01–D08 блокируют честное объявление предметного сценария проверенным. Синтетические fixtures позволяют параллельно писать код, но не закрывают эти задачи. D11 блокирует живую проверку MAX. D12 блокирует окончательную фиксацию комплекта сдачи. D13 блокирует включение ввода реальных чувствительных данных, а не разработку тестового режима.

## 2 Что собрать для каждого предложения

- [ ] Постоянный supplier_id, seller_sku и отдельный variant_id для модели/модификации/комплектации.
- [ ] Категория и точная ссылка на профиль параметров.
- [ ] Каждая опубликованная характеристика с единицей, состоянием known/unknown/conflicting и источником.
- [ ] Точная цена комплектации в рублях; пометка exact/from/unknown; дата проверки.
- [ ] Доставка: включена/отдельно/неизвестна/противоречива, сумма и условия; неизвестное не заменять нулём.
- [ ] Приём электронного сертификата именно по этому предложению, с источником либо unknown.
- [ ] Наличие необходимого договора с фондом, отдельное от приёма ЭС; при отсутствии подтверждения unknown.
- [ ] Наличие и условия поставки, контакты продавца, URL и дата каждого значимого источника.
- [ ] Проверяющий и срок следующей проверки; основание разрешённого получения/использования данных.

Ortonica и Medicamarket — кандидаты из принятой постановки. Их конкретные SKU, актуальные цены, условия договора и разрешение на автоматическое обновление ещё надо получить; синтетические examples не заполняют эти сведения.

## 3 Что собрать для маршрута

- [ ] Регион, категории изделий и точное содержание опубликованных условий.
- [ ] Список handler_id из фиксированного реестра predicates и связь каждого условия с источником.
- [ ] Какие сведения устанавливаются по ответу пользователя, какие требуют подтверждения поставщика, какие решает организация.
- [ ] Обязательные приложения, приложения при наличии и документы представителя.
- [ ] Правильный адресат, контакт, место подачи и порядок действий для выбранного региона.
- [ ] Утверждённый макет произвольного заявления; он не называется официальной обязательной формой без основания.
- [ ] Даты проверки, review_due_at, проверяющий, действие при отзыве или изменении правила.
- [ ] Эталонные примеры preliminary_match, needs_clarification, blocked и not_covered.

Исходная ссылка для проверки — [маршрут МФЦ Алтайского края](https://mfc22.ru/uslugi/svo/veteranam/17227/). Полные условия нужно сохранить в разрешённом снимке/ссылках и проверить перед активацией. Синтетический `route.example.json` содержит демонстрационные условия и placeholder чек-листа; он специально не пригоден для реального обращения.

## 4 Файлы и база данных выполняют разные роли

| Данные | Постоянное место | Формат и доступ |
| --- | --- | --- |
| Подготовленные публичные пакеты | Репозиторий `data/`, затем PostgreSQL | JSON UTF-8; версии и hashes; источники только при допустимости использования |
| Активный указатель release | PostgreSQL `data_releases` | Ссылка на неизменяемый release и аудит активации |
| Статус отзыва/проверки пакета | PostgreSQL `data_lifecycle` | Mutable metadata отдельно от content hash; изменение аудитируется |
| Identity MAX | `user_identities` | Внутренний owner_id, HMAC lookup key, зашифрованная цель доставки |
| Кейсы и служебные версии | `cases`, `input_revisions`, `input_candidates` | Ограниченные индексируемые ID/состояния отдельно от зашифрованного payload |
| Preview, подтверждения, manifest | `result_previews`, `confirmations`, `document_manifests` | Immutable encrypted payload; ссылки owner/case/revision/epoch |
| Задания и доставка | `inbox_events`, `jobs`, `outbox_messages`, `send_attempts` | Минимальные ссылки/состояния, зашифрованный чувствительный payload; fence/lease |
| Документы | Приватный volume `/var/lib/tsr/blobs/` | Зашифрованные blobs; права на чтение задаёт ArtifactRecord в БД |
| Временные ciphertext blobs | `/var/lib/tsr/staging/<job_id>/<fence_token>/` | Серверные имена, без публичной раздачи; orphan cleanup |
| Метаданные документов | `document_bundles`, `document_artifacts` | Manifest hash, формат, срок, статус и приватная ссылка |
| Токены вложений | `uploaded_attachments` | Ciphertext + owner/artifact/manifest привязка, без логирования |
| Удаление и очистка | `case_tombstones`, `cleanup_requests` | Минимальные ID, epoch, статус очистки и журнал для восстановления backup |
| Бэкапы | Защищённое отдельное место размещения | Зашифрованные БД/файлы, отдельно ключи и порядок восстановления |
| Секреты | Secret files/mounts | В репозитории только фиктивные значения и имена |

JSONB индексируется для публичного каталога и правил. Пользовательские назначения и реквизиты нельзя складывать туда в открытом виде ради поиска. Публичные материалы эксперимента содержат только агрегаты; сырые наблюдения пользователей хранятся в разрешённом закрытом контуре, без добавления в fixtures.

## 5 Сроки и очистка

Настройки принятой архитектуры: кейс/manifest — 90 дней после активности, бинарные файлы — 7 дней, обработанный чувствительный inbox payload — до 24 часов, минимальные dedupe keys — 30 дней, backup — 7 дней. Задача D13 согласует эти настройки перед пилотом. Исторический удалённый бинарный файл автоматически заново не генерируется.

Cleanup удаляет просроченные handles/candidates/previews, ciphertext событий, временные blobs без активного claim, просроченные артефакты и удалённые кейсы. Последовательность согласуется с foreign keys: минимальный dedupe tombstone может остаться без удалённого payload. Ключи восстановления не хранятся в том же backup без отдельной защиты. Restore применяет журнал удалений до открытия доступа пользователям.

## 6 Образцы в комплекте

| Образец | Для чего использовать |
| --- | --- |
| `examples/category-profile.example.json` | Структура профиля; поле и оператор пока демонстрационные |
| `examples/catalog.example.json` | Три вымышленные комплектации: совпадение, отличие и unknown |
| `examples/sources.example.json` | Структура provenance; example.invalid намеренно не является реальным источником |
| `examples/route.example.json` | Форма будущего RoutePack; не полный проверенный маршрут |
| `examples/demo-cases.example.json` | Синтетический ввод без реальных реквизитов |
| `examples/golden-cases.example.json` | Пять эталонов: три сравнения/расчёта, отказ непроверенного маршрута и неприменимость сертификата |
| `examples/template-registry.example.json` | Список будущих шаблонов; сами бинарные шаблоны и шрифт ещё не созданы |
| `examples/release-manifest.example.json` | Связи и hashes восьми типов пакетов: пример связывает семь исходных JSON; это staging-образец, активацию блокируют отсутствующие assets и непроверенные данные |

При подготовке реального пакета создаются новые ID/версии, корректные источники и реальные проверки. Нельзя просто поменять `synthetic` на `public_snapshot` или `draft` на `reviewed`, оставив демонстрационные данные и отсутствие доказательств.
