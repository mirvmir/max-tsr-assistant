# Проверка первого сценария

Сценарий использует только синтетические данные. Не вводите персональные сведения в этот эмулятор. Он показывает реальные тексты диалога и выполняет все внутренние шаги, но не отправляет сообщения в MAX.

## Карточка покупки

После первого запуска из README выполните:

```bash
docker compose exec app tsr demo --scenario purchase --download-dir /tmp/tsr-purchase --show-dialog
mkdir -p var/purchase
docker compose cp app:/tmp/tsr-purchase/. var/purchase/
```

Каждый запуск создаёт новый demo-кейс; в каталоге могут остаться PDF от предыдущих запусков. Количество файлов текущего запуска указано в `files=` и строках `Downloaded:`.

| Шаг | Что делает эмулятор | Что проверить в диалоге |
| --- | --- | --- |
| 1 | Создаёт кейс с явной ролью «Для себя» | Назначение demo и роль видны; в MAX роль выбирается кнопкой до создания кейса |
| 2 | Вводит ширину сиденья 420 мм, массу пользователя 100 кг, складную конструкцию «да» | Каждое значение показывается кандидатом и подтверждается отдельно |
| 3 | Вводит 100 000 ₽ сертификата и применимость «да» | Сумма отображается в рублях; неизвестное не превращается в ноль |
| 4 | Сравнивает предложения, выбирает первое подходящее | Видны модель, комплектация, поставщик, источник и ограничения остальных предложений |
| 5 | Выбирает карточку покупки | Точная цена 120 000 ₽, доставка включена, расчётная разница 20 000 ₽; одобрение помощи не обещается |
| 6 | Подтверждает замороженный preview | В выводе одна SHA256-строка preview/manifest; автоматический smoke отдельно проверяет их равенство |
| 7 | Дожидается worker и запрашивает файл через «Мои материалы» | `ready`, `files=1`; полученный файл начинается `%PDF-` |

Откройте PDF. Проверьте кириллицу, DEMO, параметры, цену/сертификат/разницу, поставщика и версии источников. Технические hash и IDs могут быть в документе как provenance; пользовательские кнопки имеют понятные русские подписи.

## Черновик обращения

```bash
docker compose exec app tsr demo --scenario support --download-dir /tmp/tsr-support --show-dialog
mkdir -p var/support
docker compose cp app:/tmp/tsr-support/. var/support/
```

Ожидается `ready`, `files=4`: заявление DOCX, заявление PDF, карточка изделия PDF, чек-лист PDF. Эмулятор подтверждает регион `ru-alt`, положительный ответ на модельное условие, имя «Демонстрационный Заявитель» и синтетический адрес. Все четыре файла относятся к одному frozen manifest. Статус — предварительное соответствие модели; заявление не отправляется и не является официальным бланком.

Дополнительные команды: `tsr demo --scenario both` запускает обе ветки; `--role representative` проверяет роль представителя. Полный текст и кнопки видны с `--show-dialog`.

## Ручная проверка UI в подключённом MAX

После настройки HTTPS, доверенного TLS и тестового бота по runbook:

1. Начните личный диалог. Выберите роль, затем пройдите значения первого сценария. Пользователь видит отдельные варианты «Не знаю», «Назад», «Продолжить», «Помощь», «Мои материалы».
2. Исправьте одно значение до подтверждения; нажмите старую кнопку подтверждения. Должно появиться безопасное сообщение об устаревшей кнопке, без подмены последнего значения.
3. Через «Назад» смените предложение или тип результата. Ввод должен сохраниться, прежнее подтверждение изменившегося результата перестаёт действовать.
4. На длинном кандидате/preview пролистайте все части. Подтверждение доступно после последней части; документ содержит полное подтверждённое значение. История материалов разбита на страницы.
5. Получите файл в мобильном и веб-клиенте, вернитесь в кейс и откройте материалы повторно. Это отдельная обязательная проверка живого MAX: локальные тесты её не заменяют.
6. Для старого результата требуется явное согласие с предупреждением; при неопределённой доставке повтор возможен только после предупреждения о дубликате.
7. Удалите кейс с подтверждением, попробуйте его старые кнопки. Доступ должен быть отозван сразу. Затем выполните `tsr cleanup`; повторная очистка безопасна.

В этой поставке шаги живого MAX ещё не выполнены: нет токена, публичного HTTPS endpoint и сессии клиента. Сквозной локальный сценарий и автоматические проверки перечислены в отчёте реализации.
